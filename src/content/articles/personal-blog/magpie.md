2026 年 9 月 23 日，yetone 在 GitHub 上建了一个新仓库。到 11 月初，这个叫 magpie 的项目拿到了三万两千 star、两千八百个 fork、六千九百多个提交、三千三百多个发布 tag——中间只隔了六个星期。比数字更有意思的是它的 README 里那句轻描淡写的话：这个仓库不收 pull request，代码的写作、评审、合并和发布由 agent 完成。

这篇文章分两半：前一半讲 magpie 作为产品是怎么设计的，后一半讲它背后那套“AI 自己维护项目”的机制。后者是我认为真正值得反复看的部分。

## magpie 解决的是一个多到让人烦躁的问题

先把作者背景补齐。yetone 是国内开源圈的老面孔：给 Neovim 写过 avante.nvim（把 Cursor 式的 AI 编辑体验搬进 Vim 生态），做过 OpenAI Translator，2026 年又连续做了 Alma 和 Cumora 两个 AI 产品。他写工具有一个一贯的取向：不发明新范式，把已经很火的东西之间那些别扭的缝抹平。

magpie 抹的缝是模型配置。今天的编码 agent——Claude Code、Codex、Gemini CLI、OpenCode……每一家都把模型写在自己的配置文件里，格式不同、路径不同、key 不同。你订了 Kimi 的套餐，它只能在支持 Kimi 的那几个 agent 里用；你在 Claude Code 里用得很顺手，换个 agent 又要从头配一遍。订阅制套餐和 API key 之间、多个账号之间、多个提供商之间，全是人工切换。

magpie 的答案是一个常驻菜单栏（现在也有 Windows、Linux、Docker 和终端版）的本地网关：

- 任何 agent 配任何模型。在同一个可搜索列表里选 `provider/model`，magpie 以原子方式改写那个 agent 自己配置文件里唯一要紧的一个键，注释、顺序、格式都不动。
- 一个提供商到处用。API key、本地模型，或者你已登录的 Claude、ChatGPT、Copilot、Gemini、Grok 订阅，都可以被所有 agent 共享。
- 配额用完自动续命。一个提供商的下一个账号顶上，路由组再切到别的模型或提供商，agent 根本看不到报错。
- 隐私脱敏。开关打开后，prompt 里的 key、密码、邮箱在你本机被替换成占位符，请求出门前就脱敏，回复回来再原样放回，流式文本和工具调用参数都处理。同一个值永远映射到同一个占位符，所以对话、prompt 缓存、思考签名都不会失效。

![图：阿鼠在黑板前讲解 magpie 网关架构：各家 agent 的请求经本地网关 127.0.0.1:3425 流向各家模型与订阅](https://img.arkblob.ccwu.cc/articles/magpie/chapters/02-gateway/gateway-blackboard-v2.jpg)

架构上没有黑科技：一个跑在 `127.0.0.1:3425` 的本地网关，同时说 OpenAI Chat、OpenAI Responses、Anthropic Messages 和 Gemini 四种协议，并在它们之间互译——流式、工具调用、推理内容都翻。所有 agent 的请求都进这个网关，网关再根据路由规则分发到你配置的 key、订阅账号或本地模型上。路由组可以按 smart（优先用最快重置的配额）、order（主备）、rotate（轮换）、usage（最省）、pace（按小时配速）几种策略展开，组里还能嵌套组。意图路由再加一层：一个小模型先读每一轮新请求，测试代码送去强模型，快问快答送去便宜模型。

产品覆盖面是它涨星快的原因之一：README 列出的兼容 agent 超过一百个，从 Claude Code、Codex 到各种小众 CLI，任何吃 base URL 的工具都能直接指过来。插件系统跑在 Bun 上，社区仓库里已经有了各家订阅的登录插件和一批网关中间件（改参数、模型映射、敏感词过滤之类）。

## 真正值得研究的部分：代码是 agent 写的

三万 star 的项目六个星期做完，一个人加几个维护者，靠传统工作流是不可能的。magpie 的做法写在仓库根目录的几个文件里，摊开看非常直白。

`CLAUDE.md` 只有两行：`@AGENTS.md`、`@LESSONS.md`。Claude Code 来干活时，被直接指到 agent 的作业规范和历史教训上去。`AGENTS.md` 告诉 agent：改任何子系统前先读对应的设计参考文档并核对源码链接；提交评审按同一套文档规则走；改代码前先读 `LESSONS.md`。

`docs/subsystems/` 里有十五份子系统设计参考，每份写清楚这个子系统的职责边界、状态转移、运行路径、失败行为和约束，并链接到具体源码符号。评审一份 PR 的流程是明文的：找到受影响的子系统、对着 diff 核对声称的行为变化、确认引用的测试真的覆盖了声称的行为。文档不是装饰，是 agent 的作业规程。

节奏有多快？`LESSONS.md` 的开篇记录：2026-10-05 这一天有 220 个提交、约 170 个发布，其中约 40 个是在修当天或前一天发布引入的问题。每个 tag 都等一次绿色构建，每个超过四百行的提交都在正文里写明跑了什么。提交信息全部带领域前缀——`gateway:`、`routing:`、`docker:`、`icon:`——一眼能看出这行改动属于哪里。这不是人熬夜手打的纪律，是 agent 按模板生成的纪律。

![图：夜晚的灯下，一桌戴眼镜的阿鼠逐条复审当天的提交，教训写进墙上的 LESSONS.md 卷轴](https://img.arkblob.ccwu.cc/articles/magpie/chapters/03-night-review/ch03-night-review.jpg)

人不在写代码的环路上，人在规则的环路上。magpie 把“维护者”这个角色拆成了三层：

第一层是验收标准。`docs/code-standards.md` 把一次合并的门槛写成可执行的清单：修复必须带一个“没有这个修复就会红”的测试，评审者要把旧代码放回去跑一遍确认它真的红；测试永远不许碰网络，供应商页面用 httptest 从真实字节构造；必须在沙箱 HOME 里跑，不许读写真实的 `~/.codex`、`~/.claude`；跑了哪些检查、每个检查输出什么，都要写进提交正文，没跑的检查也要如实写“没跑”。

第二层是夜间复审。每天结束，当天的提交被逐条过一遍：什么又修了一次、什么不该合并、什么验证得太薄。发现的东西变成 LESSONS.md 里的一条条教训，每条是“规则—为什么—证据”三段，证据直接引用具体的提交哈希和 issue 编号。第二天任何 agent 开工前先读这个文件。

第三层是规则晋升。一条教训如果在三个不同的日子里被复审看到，就升级进 code-standards.md，成为硬规则。教训不是越攒越多的流水账，而是会沉淀、会晋级、会被下次评审执行的制度。

![图：阿鼠讲教训的升级路径——同一条教训被连续三天看到，就从 LESSONS.md 升为 code-standards.md 硬规则](https://img.arkblob.ccwu.cc/articles/magpie/chapters/04-lessons/lessons-path-v2.jpg)

## 教训文件里到底长什么样

LESSONS.md 是这个仓库最生动的文件，八百多行全是带血的案件记录。随便摘几条感受一下口味：

- **复现报告者用的确切场景，用他用的那个界面，才能说修好了。** 证据：#834 回归了四次，每轮都只修了截图里那个 agent，报告者用的是另一个。
- **“在 main 上也一样红”不是基线。** 大量提交踩着红测试发版，其中有的红是真 bug（一个数据竞争、一个限速缺口）。规则变成：红测试要么当场修掉根因，要么在同一提交里开 issue 写明原因。
- **豁免按值在协议里的位置划界，永远不按字段名划界。** 一次安全修复放过所有带 `signature` 键的对象，结果工具调用参数里模型自己写的 `"signature": …` 夹着数据库密码原样发给了供应商。
- **文档里点名的安全洞就是未修复的 bug。** 子系统文档里写着“没有 Host 校验，DNS rebinding 可以绕过同源”，复审当晚在 main 上复现成功，随即修掉。
- **一台机器同时只跑一个全量套件。** 三个并行全量测试把机器打到 load 300+，全部超时，没有任何记录能证明套件通过过。之后提交正文里出现“through suite-lock”。
- **社区的补丁当天评审或答复。** 一个 reporter 带复现和红测试的补丁挂了三天没人接，直到 CI 自己红掉才被原样移植进来——这条后来写进了硬规则。

这些教训的可贵之处在于它们几乎全是 agent 犯的错：并行会话互相覆盖对方的发布文件、测试在真实时间上断言导致跨时区 CI 变红、把 24MB 回复整个读进内存拖到超时。它们不是人类工程师的老生常谈，而是大规模 agent 协作暴露出来的新故障模式，被一条条抓出来变成规则。

社区协作也是 agent 在前面。`docs/contributors.md` 写明了流程：任何社区 PR 先做“查伤害”检查——碰 `.github/`、加网络地址、传凭据、加二进制 blob 的一律停下来等人看；然后是关单规则、署名规则（reporter 的补丁要带 `Co-authored-by`）、拉黑规则（agent 只提议并附证据，人决定）。agent 提议、人类裁决，权限边界写得清清楚楚。

## 这套东西说明了什么

看完整套机制，我自己的几点感受。

第一，文档的角色变了。在传统项目里，架构文档写给未来的贡献者看，通常是过期的。在 magpie 里，subsystems 文档是 agent 的操作手册和评审依据，改动必须同步更新对应参考，文档过期等于作业规程失效。文档从“注释”变成了“法律”。

第二，经验沉淀有了可执行的形态。“代码评审意见”在大多数项目里是 Slack 里的一句吐槽，下一个 PR 还会犯。magpie 把它变成 LESSONS.md 的三段式条目，再配上“三天晋级”的机制，让教训有明确的去向和生命周期。组织记忆不再依赖人记得，依赖文件被读。

第三，质量闸门必须机器可执行。因为执行者是 agent，所有规则都得写成可判定的形态：测试要在沙箱、跑 `./...` 而不是挑包、提交正文要写跑了什么。含糊的评审意见（“注意代码质量”）在 agent 工作流里毫无意义，能落成命令和清单的才有用。

第四，人的位置上移了。yetone 不写代码也不逐条评审，他维护的是规则系统：验收标准、教训晋升、社区策略。这大概是目前“一个人维护三万 star 项目”唯一现实的方式——不是更努力，而是把维护者做成了立法者。

当然也要看到另一面：这个模式目前强依赖一个品味极高、投入极大的维护者把规则写对；3400 个 open issue 说明吞吐量上去之后社区侧的消化仍然是瓶颈；而且规则体系本身（LESSONS.md 898 行、code-standards.md 不断膨胀）长期能不能保持可读，是个开放问题。AI 自己维护项目不是无人化，是换了一种很重的脑力劳动。

magpie 作为产品，解决的是“模型选择太分散”这个真实但未必永恒的问题；而它示范的“规则即维护”的那套机制，适用期大概会长得多。想亲手看看的，仓库在 [github.com/yetone/magpie](https://github.com/yetone/magpie)，先读 AGENTS.md，再读 LESSONS.md——按它自己的规矩，这个顺序不能反。
