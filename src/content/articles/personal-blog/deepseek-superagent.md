> DeepSeek 最近发布了 Super-agent 的设计文章《Super-agent 设计探索：迈向更自主的 Agent 系统》，并开源了原型 `dsh-superagent-prototype`。先说清楚：它不是新框架——原型是 DeepSeek Harness 之上的一个插件，示范的是"常驻 Agent 如何组织"这套架构模式；且开源不等于内部版本，部分设计是未来方向。我读完了文章、九篇设计文档和原型源码，这篇拆解只关注一件事：这套设计背后的理念是什么，它可能怎么实现。

![图：A鼠讲师讲解 Super-agent——黑板上是 Router 与三个 Worker 的架构草图，铃铛代表事件驱动，小狗代表 Watchdog](https://img.arkblob.ccwu.cc/articles/deepseek-superagent/cover-v2.jpg)

## 一、问题定义：注意力是唯一的标尺

原文的出发点，一句话就能讲完：

> 单任务的上限取决于模型能力，多任务的上限取决于人的注意力。

一个人同时只能跟进 3-5 个活跃 Session。当 Agent 需要人逐条派活、逐个切换上下文时，瓶颈根本不在模型，在人身上。原文由此推出 Super-agent 的四个特征——连续（跨信道是同一个 Agent）、高效（并发多任务）、主动（观察环境、该出手才出手）、持久（常在线、故障自愈）。

**这四个特征是表象，背后有一把标尺：每一个设计决策都在回答"这件事让不让人操心、让谁操心、操心几次"。** 后面讲到的每个机制，都值得用这把标尺重新量一遍。

值得一提的还有方法论：原文反复强调这些问题与传统计算机系统问题同构——中断合并、Cache 管理、分支预测、无状态服务、看门狗。"我们没有发明新理论，只是把经典思想搬进 Agent 系统。"这个思路本身就很值得学：给 Agent 基础设施做设计时，先去旧系统里找答案。

## 二、五个设计锚点

整篇文章可以收拢成五个可复用的设计锚点。每个锚点先讲它在防什么失效，再讲设计本身。

### 锚点 1：分层——Router/Worker 不是 Agent Team

看结构图容易误读成"Agent Team / 多智能体编排"，不是。差别在职责的耦合方向：

- Agent Team 的 Lead 要深入单个任务内部：拆解步骤、规划子任务、高频协调成员，Lead 的推理负载随任务复杂度增长；
- Super-agent 的 Router **结构上不碰任务内部**：只做任务间的高层关联与分派，甚至不配执行工具，原文实践发现用轻量模型就够。

一个是"带团队干活的架构师"，一个是"前台加派活的调度员"。原文给了个有趣的判定：用提示词约束 Agent Team 主会话"不亲自执行、只分派"，形式上就成了双层架构——但这靠提示词维系，而他们的消融实验恰好证明提示词靠不住（中性提示下模型 5 次有 5 次自己干活不委派）。**Router/Worker 是把"分不分工"从模型的临场判断升级为结构保证。**

实现猜想：一个常驻的主会话加一个工具白名单（只给分派/订阅/回复类原语，不给执行类工具），就是一个最小可用的 Router。分派时给 Worker 建独立会话、注入任务上下文快照，Worker 的产出只回到 Router，绝不直接对外。

### 锚点 2：全双工 Loop——run() 与 start()

经典 agent loop 的隐含假设：模型发起工具调用 → 阻塞等待 → 结果回来 → 下一步。整个会话是半双工的，工具跑多久会话就聋多久。

Super-agent 的改法是把耗时动作异步化：`start()` 立即返回，后台执行；完成后**结果作为一条新消息投递回会话**（事件化）；`stop()` 可主动终止；期间用户新输入在当前推理步结束后即被处理。注意这里没有引入线程或协程并发——循环还是单线程的，只是把"等待"从阻塞变成了事件投递，就足以让会话变成全双工。

实现猜想：把工具协议分叉出 async 变体，宿主维护一张后台任务表，任务完成时把结果包装成普通消息插进队列。改造成本集中在宿主的调度层，不动模型交互协议。

### 锚点 3：事件驱动——Trigger 与订阅直通

这是原型里工程最重的部分，核心是给"会话之外的世界"建模：

- **Trigger**：环境中不可变的事件单元（IM 消息、PR 评论、CI 结果）。不可变是审计和幂等的基础——同一个 Trigger 被接受两次只会建一个工单；
- **两级过滤**：先程序规则（Fast Path，白名单/来源/范围，代码判定）再模型研判（Slow Path，提示词策略），绝大多数噪音死在第一级；
- **订阅直通**：按初始事件创建 Worker 并建立订阅后，同一 Thread 的后续事件由**程序直接转发**给订阅者，不再过 Router。这是"Fast/Slow Path"思想的第二次应用——路由本身也有快慢路径。

数据：直通机制去掉后用户侧完成时间基本不变，但 Router 决定量 +30%、token +37%。即**直通省的不是用户的等待，是调度者的负载**——这个区分对容量规划很关键。

实现猜想：事件总线的最小形态是一张订阅表加一个投递循环；难的不是转发，而是 Trigger 的不可变存储、投递 trace 和去重语义——这三样决定这套机制是玩具还是基础设施。

### 锚点 4：存算分离 + Watchdog——常驻的前提

两层解耦：①计算与状态分离——Agent Loop 做成无状态容器，状态进数据库，实例可水平扩展可重启；②Loop 与执行环境分离——环境难复制就不复制，留在用户设备上，云端只下发命令，端侧轻量 daemon 执行（BYOM，支持间歇在线设备）。

Watchdog 是"用 Agent 管理 Agent"理念最直接的应用：主系统外挂一个独立的 Watchdog Session，定时消息驱动，监控对象是**任务进展**而非进程存活（模型陷入无效循环时进程是健康的）；发现异常可以修提示词、调触发规则、重启组件——用自然语言运维一个 Agent 系统。

实现猜想有个梯度，从便宜到贵：旁路监控（独立会话只读运行日志，产出告警）→ 有限干预（白名单管理 API）→ 完全自治（修改主系统提示词与规则）。原文坦承第三档的安全隐忧最大。第一步的成本极低——只要运行日志是结构化的，监控会话就能直接消费。

### 锚点 5：工单化的领域模型——常驻 Agent 的任务抽象

原型把前面四个锚点落成了一套干净的领域模型（Source/Trigger/Thread/Eval/Ticket/Mandate/Assignment/Subscription/Channel/Policy），本质是把**操作系统的进程管理思想应用到 Agent 任务管理**：长驻对话是"系统进程"，一次性工作是"有生命周期的工单"。

![图：dsh-superagent 领域模型——事件到工单的完整管线，每个箭头都在防一种失效](https://img.arkblob.ccwu.cc/articles/deepseek-superagent/domain-model-pipeline.jpg)

它的几个设计选择，每个都在防一种失效：

- **Trigger 不可变 + Source 持有读位置** → 防重启重放、防重复处理；
- **Eval（Gate 代码 + Assessment 模型）无状态** → 防规则热更新时新旧判定不一致；
- **Mandate 记录授权依据（Policy 版本/范围/强度），工单结束不自动撤销** → 防规则变更波及在跑任务；恢复已结束工单前按当前 Policy 复验 → 防用过期授权续命；
- **订阅绕权限闸门但"授予上下文不授予权力"** → 防借上下文夹带越权指令；
- **Effects/Outbox：消息发送先落库再异步执行，同一事务** → 防对外输出丢失或重复；
- **worker 槽位 + 后台任务 30 分钟上限 + 交付即释放** → 防并发失控和僵尸任务。

还有一个贯穿全部设计的哲学细节值得单独点出：**权限由宿主代码强制，提示词和消息内容只是决策输入**——外部文本永远进不了权限判定回路。这是对提示词注入的结构性防御，比任何"请忽略指令"式的提示词防御都可靠。

## 三、深入：分层的本质与"用 Agent 管理 Agent"

### 3.1 分层的本质：两种连续性的分离

回到根本权衡：所有事件进一个 Session，上下文最连续但串行低效；每个事件一个 Session，并发最高但上下文割裂、交互混乱。Router/Worker 是对这个矛盾的工程化拆解——**把"全局的连续性"和"任务的隔离性"分配给两种不同的组件**：

- Router 是**全局序点（Sequence Point）**：所有跨任务信息与决策在此汇总，它就是整个系统的"内存一致性模型"。它便宜（轻量模型、短输出）、不碰任务、不需要工具——因为它只回答三个问题：这事件要不要接？给谁？要不要回话？
- Worker 是**隔离的执行域**：独立上下文、完整工具、最强模型，产出只向 Router 汇报，绝不直接对用户输出。

这个分层有个精妙的副产品：**用户面前的"一个 Agent"是 Router 层制造出来的假象**。原文的原话——Session 应该是系统实现细节，不应是用户认知负担。有没有能力把 session 从用户视野里藏起来，是"Agent 产品"与"Agent 框架"的分野。

为什么单 Router 不容易成为瓶颈？批处理：推理期间到达的事件积压，下一轮合并注入。Router 每步是长输入短输出，Prefill 并行摊薄了延迟——实测 40 条/分到达率下，单个决定分摊的推理时间反而从 6.4s 降到 1.6s。再往上扩容时，Router 可以水平切分，但切分粒度是连续性与吞吐量的新权衡——原文坦承在全局记忆问题解决前这个权衡一直存在。

![图：Router: decide, never do——分派箭头指向 W1/W2/W3，右侧 watchdog 巡检一排服务器](https://img.arkblob.ccwu.cc/articles/deepseek-superagent/ch03-router-worker-watchdog.jpg)

### 3.2 用 Agent 管理 Agent：控制回路的外置

传统分布式系统的可靠性靠外部控制回路（watchdog、supervisor、k8s controller），Super-agent 把这个思想推进一步：**Agent 系统的故障模式大多数不是进程崩溃，而是行为失当**——无效循环、方向偏离、该停不停。进程监控管不了这些，必须有个具备语义理解能力的东西来盯。

所以 Watchdog 本身就是一个 Agent Session：读运行记录、判断进展、执行修复动作、向人汇报。这就是"用 Agent 管理 Agent"——**当被管理对象的行为本身是智能行为时，管理者也必须具备智能**。

这个理念有三档落地梯度（上一章的猜想展开说）：

1. **旁路监控**：独立的健康检查会话，只读运行记录，产出告警——零侵入，任何有结构化 trace 的系统今天就能做；
2. **有限干预**：Watchdog 可调用白名单管理 API（调参数、改配置、重启会话）；
3. **完全自治**：Watchdog 修改主系统的提示词与规则——原型支持到这一级，也是安全争议最大的一档——谁来监控监控者？这个问题原文没有回答，留给读者。

一个务实的判断：从第 1 档起步几乎总是正确的——先验证运行记录里确实存在"机器可判读"的健康信号，再谈干预。

## 四、边界：明确不做什么

最后划边界。这套设计当前的适用范围与未解问题：

- **研究原型，不是产品**。README 明说参考用，部分文章描述的能力（异步 Loop 默认开启、存算分离、Watchdog）尚未在原型中实现，引用时要有这个限定；
- **领域模型不可照搬**。Source/Policy/Mandate 那套是为"监听 GitHub/飞书、全自动接单"设计的，换成别的场景需要重新裁剪授权模型；
- **四个开放问题**原文自己承认：Router 何时切分、脱离 Session 的人机交互形态、多实例 A2A 边界、安全与隐私（云端 Loop 被攻破则全部端侧设备暴露，凭据不该进入模型上下文）。

如果把这套思想收敛成几条可带走的判断：

1. 需要必然发生的约束，放进结构，不放进提示词；
2. 确定性判断固化成代码，语义判断才交给模型——过滤和路由都有快慢路径；
3. 上下文窗口当 Cache 管理：内联高频、外置低频、留好"下一跳"引用；
4. 环境难以复制就不要复制——把计算搬到环境旁边，而不是相反；
5. 监控智能行为需要智能监控者，但监控者自身要最小化权限；
6. 对外输出走"先落库再发送"的事务语义；
7. "主动"的正确度量不是做了多少事，而是替人省了多少注意力——安静地做对，比喧哗地做多难得多。

一句话收尾：Super-agent 最大的借鉴价值，不在于提供了什么现成工具，而在于它用调度、解耦、看门狗这些经典系统思想，把 Agent 基础设施的系统边界从"管理一个 Loop"扩展到了"管理一群常驻 Worker 的生命周期"。单 Loop 的时代已经做扎实了，下一个时代的竞争力，藏在"Loop 之外"的基础设施里。
