> 这是写给团队的一份周会分享。背景：我们的 agent OS SDK 已经提供了 agent loop、自定义工具、技能、hook、session、trace log 这套生态，底层是 goclaw。最近 DeepSeek 开源了 Super-agent 的设计文章和原型，本文不是评测"要不要换框架"，而是把其中值得纳入我们架构雷达的设计思想摆到桌面上。

![图：A鼠讲师讲解 Super-agent——黑板上是 Router 与三个 Worker 的架构草图，铃铛代表事件驱动，小狗代表 Watchdog](https://img.arkblob.ccwu.cc/articles/deepseek-superagent/cover-v2.jpg)

## 先说清楚：这是架构模式，不是新框架

花一分钟把三个事实钉死，避免讨论跑偏：

1. **Super-agent 不是框架，是架构模式**。官方开源的 `dsh-superagent-prototype` 是 DeepSeek Harness 之上的一个插件，Demonstration 的是"常驻 Agent 如何组织"这套模式。它依赖 Harness 的会话、预设、收件箱机制，脱离 Harness 跑不起来——所以它不是一个我们要"迁移到"的东西，而是拿来对照的镜子。
2. **开源原型 ≠ 内部版本**。README 原话：与内部实现及设计文章描述不完全一致，部分设计是未来方向。引用实验数据时要带上这个限定。
3. **研究代码，工程粗糙度真实存在**。官方自己说"大量工程由 coding agents 完成"。值得学的是设计，不是代码本身。

本文的素材：设计文章《Super-agent 设计探索：迈向更自主的 Agent 系统》（2026-10-31 公众号）、原型仓库的 9 篇编号设计文档与源码。

## 一、问题定义：注意力是唯一的标尺

原文的出发点，一句话就能讲完：

> 单任务的上限取决于模型能力，多任务的上限取决于人的注意力。

一个人同时只能跟进 3-5 个活跃 Session。当 Agent 需要人逐条派活、逐个切换上下文时，瓶颈根本不在模型，在我们自己身上。原文由此推出 Super-agent 的四个特征——连续（跨信道是同一个 Agent）、高效（并发多任务）、主动（观察环境、该出手才出手）、持久（常在线、故障自愈）。

**这四个特征对我们不重要，重要的是背后那把标尺：每一个设计决策都在回答"这件事让不让人操心、让谁操心、操心几次"。** 后面五个锚点，每一个我都会用这把标尺重新量一遍——这也是判断哪些值得进我们架构雷达的标准。

值得一提的是方法论：原文反复强调这些问题与传统计算机系统问题同构——中断合并、Cache 管理、分支预测、无状态服务、看门狗。"我们没有发明新理论，只是把经典思想搬进 Agent 系统。"这个思路本身就很值得我们学：给 Agent 基础设施做设计时，先去旧系统里找答案。

## 二、五个设计锚点 vs 我们的现状

先给结论表，再逐个展开。标注含义：**已有基础**=我们 SDK 已具备对应能力，方向对了；**需要增强**=有对应物但缺关键属性；**需要新建**=我们没有对应物，但可以从 SDK 现有概念自然延伸。

| 设计锚点 | Super-agent 的做法 | 我们的对应物 | 判定 |
|---------|-------------------|-------------|------|
| 分层：Router/Worker | 常驻 Router 统一交互与分派，Worker 隔离执行 | agent loop + session，无强制分层 | **需要增强** |
| 全双工 Loop | start/stop 异步执行，结果事件化回注 | agent loop 是同步阻塞模型 | **需要增强** |
| 事件驱动 | Trigger→两级过滤→订阅直通 | hook 是进程内回调，无事件路由 | **需要新建** |
| 存算分离 + Watchdog | 无状态 Loop 上云 + 端侧 daemon + 外部看门狗 | session 持久化 + trace log | **需要增强** |
| 插件化内核 | Source 插件协议 + 领域模型 + 主机强制权限 | SDK 工具/技能/hook 注册机制 | **已有基础** |

![图：五个设计锚点逐行对照——每行一个机制图标，三列标注已有基础、需要增强、需要新建](https://img.arkblob.ccwu.cc/articles/deepseek-superagent/ch02-anchor-matrix.jpg)

### 锚点 1：分层——Router/Worker 不是 Agent Team

这是全文我最想讲透的一个误读风险。看结构图容易觉得"这不就是 Agent Team / multi-agent 编排吗"，不是。差别在**职责的耦合方向**：

- Agent Team 的 Lead 要深入单个任务内部：拆解步骤、规划子任务、高频协调成员，Lead 的推理负载随任务复杂度增长；
- Super-agent 的 Router **结构上不碰任务内部**：只做任务间的高层关联与分派，甚至不配执行工具，原文实践发现用轻量模型就够。

一个是"带团队干活的架构师"，一个是"前台 + 派活的调度员"。原文还给了个有趣的判定：你用提示词约束 Agent Team 的主会话"不亲自执行、只分派"，形式上就成了双层架构——但这靠提示词维系，他们的消融实验恰好证明提示词靠不住（中性提示下模型 5 次有 5 次自己干活不委派）。**Router/Worker 是把"分不分工"从模型的临场判断升级为结构保证。**

**对我们的意义**：我们有 session 概念，session 之间是平的；我们有 hook，但没有一个"只管分派、不执行"的常驻角色。值得在 SDK 层面把"Router 型 session"做成一等公民：限制工具集、限制发言权、内置分派原语。这是增强，不是重建。

### 锚点 2：全双工 Loop——run() 与 start()

经典 agent loop 的隐含假设：模型发起工具调用 → 阻塞等待 → 结果回来 → 下一步。整个会话是半双工的，工具跑多久会话就聋多久。

Super-agent 的改法是把耗时动作异步化：`start()` 立即返回，后台执行；完成后**结果作为一条新消息投递回会话**（事件化）；`stop()` 可主动终止；期间用户的新输入在当前推理步结束后即被处理。注意这里没有引入线程或协程并发——循环还是单线程的，只是把"等待"从阻塞变成了事件投递，就足以让会话变成全双工。

**对我们的意义**：我们的 loop 是同步模型。把 SDK 的工具调用协议分叉出 `async` 变体、增加"后台结果回注为消息"的投递语义，是我们在 loop 层面最值得做的一个增强——它同时是事件驱动和 Watchdog 的前置条件。

### 锚点 3：事件驱动——Trigger 与订阅直通

这是原型里工程最重的部分，核心是给"会话之外的世界"建模：

- **Trigger**：环境中不可变的事件单元（IM 消息、PR 评论、CI 结果）。不可变是审计和幂等的基础——同一个 Trigger 被接受两次只会建一个工单；
- **两级过滤**：先程序规则（Fast Path，白名单/来源/范围，代码判定）再模型研判（Slow Path，提示词策略），绝大多数噪音死在第一级；
- **订阅直通**：Router 按初始事件创建 Worker 并建立订阅后，同一 Thread 的后续事件由**程序直接转发**给订阅者，不再过 Router。这是"Fast/Slow Path"思想的第二次应用——路由本身也有快慢路径。

数据：直通机制去掉后用户侧完成时间基本不变，但 Router 决定量 +30%、token +37%。即**直通省的不是用户的等待，是调度者的负载**——这个区分对我们做容量规划很关键。

**对我们的意义**：hook 是"进程内、同步、绑定单 session"的回调；事件驱动需要的是"进程外、异步、跨 session 可路由"的事件总线。Trigger 的不可变 + 投递 trace 的设计可以直接借。判定：新建，但底座（session、trace log）都现成。

### 锚点 4：存算分离 + Watchdog——常驻的前提

两层解耦：①计算与状态分离——Agent Loop 做成无状态容器，状态进数据库，实例可水平扩展可重启；②Loop 与执行环境分离——环境难复制就不复制，留在用户设备上，云端只下发命令，端侧轻量 daemon 执行（BYOM，支持间歇在线设备）。

Watchdog 是"用 Agent 管理 Agent"理念最直接的应用：主系统外挂一个独立的 Watchdog Session，定时消息驱动，监控对象是**任务进展**而非进程存活（模型陷入无效循环时进程是健康的）；发现异常可以修提示词、调触发规则、重启组件——用自然语言运维一个 Agent 系统。

**对我们的意义**：我们有 session 持久化和 trace log——这正是存算分离的"存"和 Watchdog 的"数据源"。缺的是把 trace log 从"调试时人看"升级为"机器可消费的健康信号"。trace log → Watchdog 数据源，可能是我们**成本最低、杠杆最高**的一步：不用改 loop，不用改内核，先让一个旁路消费者读 trace 判断任务健康度。

### 锚点 5：插件化内核——我们已有的部分

原型的领域模型（Source/Trigger/Thread/Eval/Ticket/Mandate/Assignment/Subscription/Channel/Policy）全部通过 Source 插件协议接入 Harness；权限由宿主代码强制，提示词和消息内容只是决策输入——**外部文本永远进不了权限判定回路**，这是对提示词注入的结构性防御。

**对我们的意义**：我们的工具/技能/hook 注册机制就是插件化内核的雏形，方向已经对了，判定"已有基础"。值得抄的两个细节：权限模型里"宿主强制 vs 模型输入"的边界划分；以及他们的哲学第一条——每个功能先问消耗多少人的注意力，不回本就砍掉。这条可以直接进我们的设计评审 checklist。

## 三、深入：Router/Worker 的分层哲学与"用 Agent 管理 Agent"

按周会讨论的需要，把上面两个点展开讲透。

### 3.1 分层的本质：两种连续性的分离

回到原文的根本权衡：所有事件进一个 Session，上下文最连续但串行低效；每个事件一个 Session，并发最高但上下文割裂、交互混乱。Router/Worker 是对这个矛盾的工程化拆解——**把"全局的连续性"和"任务的隔离性"分配给两种不同的组件**：

- Router 是**全局序点（Sequence Point）**：所有跨任务信息与决策在此汇总，它就是整个系统的"内存一致性模型"。它便宜（轻量模型、短输出）、不碰任务、甚至不需要工具——因为它只回答三个问题：这事件要不要接？给谁？要不要回话？
- Worker 是**隔离的执行域**：独立上下文、完整工具、最强模型，产出只向 Router 汇报，绝不直接对用户输出。

这个分层有个精妙的副产品：**用户面前的"一个 Agent"是 Router 层制造出来的假象**。原文的原话——Session 应该是系统实现细节，不应是用户认知负担。我们的 SDK 把 session 直接暴露给使用者，这一层的抽象差距，就是"Agent 产品"与"Agent 框架"的分野。

为什么单 Router 不容易成为瓶颈？批处理：推理期间到达的事件积压，下一轮合并注入。Router 每步是长输入短输出，Prefill 并行摊薄了延迟——实测 40 条/分到达率下，单个决定分摊的推理时间反而从 6.4s 降到 1.6s。再往上扩容时，Router 可以水平切分，但切分粒度是连续性与吞吐量的新权衡——原文坦承在全局记忆问题解决前这个权衡一直存在。

### 3.2 用 Agent 管理 Agent：控制回路的外置

传统分布式系统的可靠性靠外部控制回路（watchdog、supervisor、k8s controller），Super-agent 把这个思想推进一步：**Agent 系统的故障模式大多数不是进程崩溃，而是行为失当**——无效循环、方向偏离、该停不停。进程监控管不了这些，必须有个具备语义理解能力的东西来盯。

所以 Watchdog 本身就是一个 Agent Session：读 trace、判断进展、执行修复动作（改提示词、调规则、重启组件）、向人汇报。这就是"用 Agent 管理 Agent"——**当被管理对象的行为本身是智能行为时，管理者也必须具备智能**。

这个理念其实有梯度，从便宜到贵：

1. **旁路监控**：独立的健康检查 Agent，只读 trace log，产出告警（我们可立即做，零内核改动）；
2. **有限干预**：Watchdog 可调用白名单管理 API（调参数、改配置、重启 session）；
3. **完全自治**：Watchdog 修改主系统的提示词与规则——原型支持到这一级，原文也坦承这是安全隐忧最大的一档（详见下一章）。

建议我们的路径：从 1 起步，验证 trace log 里确实存在"机器可判读"的健康信号，再谈 2 和 3。

### 3.3 原型的结构性启示：一个"工单化"的范本

原型把上面这套哲学落成了非常干净的领域模型，值得专门看一眼它的骨架（这也是我觉得对我们 SDK 演进最有参考价值的一张图）：

![图：dsh-superagent 领域模型——事件到工单的完整管线，每个箭头都在防一种失效](https://img.arkblob.ccwu.cc/articles/deepseek-superagent/domain-model-pipeline.jpg)

它的几个设计选择，每个都在防一种失效：

- **Trigger 不可变 + Source 持有读位置** → 防重启重放、防重复处理；
- **Eval（Gate 代码 + Assessment 模型）无状态** → 防规则热更新时新旧判定不一致；
- **Mandate 记录授权依据（Policy 版本/范围/强度），工单结束不自动撤销** → 防规则变更波及在跑任务；恢复已结束工单前按当前 Policy 复验 → 防用过期授权续命；
- **订阅绕权限闸门但"授予上下文不授予权力"** → 防借上下文夹带越权指令；
- **Effects/Outbox：消息发送先落库再异步执行，同一事务** → 防对外输出丢失或重复；
- **worker 槽位 + 后台任务 30 分钟上限 + 交付即释放** → 防并发失控和僵尸任务。

这套"事件→研判→授权→派工→汇报"的工单化模型，本质上是把**操作系统的进程管理思想应用到了 Agent 任务管理**。我们的 session 是"长驻对话"，他们把一次性工作抽象成"有生命周期的工单"——对要走向"常驻 Agent"的 SDK 来说，这个抽象值得认真评估。

## 四、边界与架构雷达：明确不做什么

先说不做什么：

- **不引入、不迁移**。dsh-superagent 绑定 DeepSeek Harness，研究原型，工程粗糙，没有"用起来"的选项；
- **不全盘照搬领域模型**。Source/Policy/Mandate 那套是为"监听 GitHub/飞书、全自动接单"设计的，我们的场景未必需要这么重的授权模型；
- **不给出"要不要跟进"的结论**。今天的目的是把选项摆上桌，判断留给架构雷达流程。

再说建议进雷达的，按投入产出排序：

| 优先级 | 雷达项 | 依据 | 第一步 |
|-------|--------|------|--------|
| P0 | trace log → Watchdog 数据源 | 存算分离+Watchdog 锚点；零内核改动 | 旁路健康检查 Agent 原型 |
| P1 | loop 异步化（start/stop + 结果事件回注） | 全双工锚点；事件驱动的前置 | 工具协议增加 async 变体设计稿 |
| P1 | Router 型 session（分派原语 + 工具限制） | 分层哲学；缓解未来多会话扩展 | 在 SDK 会话层定义 Router 预设 |
| P2 | 事件总线（Trigger/订阅直通） | 事件驱动锚点；新建成本最高 | 结合 hook 场景调研需求真伪 |
| P2 | 工单化任务抽象 | 原型领域模型；常驻 Agent 前提 | 对照 SDK 场景裁剪领域模型 |

![图：架构雷达——五个雷达目标，两个勾选进雷达，一个划掉不做](https://img.arkblob.ccwu.cc/articles/deepseek-superagent/ch04-architecture-radar.jpg)

**一句话收尾**：Super-agent 最大的借鉴价值，不在于提供了什么现成工具，而在于它用调度、解耦、看门狗这些经典系统思想，把 Agent 基础设施的系统边界从"管理一个 Loop"扩展到了"管理一群常驻 Worker 的生命周期"。我们的 SDK 已经把"一个 Loop"做扎实了，下一步的演进方向，恰恰在这些"Loop 之外"的基础设施缺口里。
