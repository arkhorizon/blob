2026 年 DeepSeek 开源了一个叫 Harness（dsh）的 agent 框架，GitHub 上已经 27 万 star。它不是又一个大模型 API 封装，而是一个能跑的完整产品：Web UI、桌面端、CLI、SDK 多种形态，聊天、工具执行、沙箱、审批、多人协作一应俱全。

但真正值得看的不是功能清单，而是一句口号背后的架构立场——**Everything is a Plugin**。模型适配器是插件，工具注册表是插件，会话日志是插件，连 agent loop 本身都是插件。这篇文章拆开它的设计，看这套思路对任何 agent 框架意味着什么。

需要说明：dsh 目前处于开发者预览阶段，官方明确未来会有破坏兼容性的变更。本文以设计为纲，细节可能随版本演进。

## 一切皆插件：没有特权内核

![图：A鼠讲师站在黑板前讲解插件树，树根向上一层层的组合包与补丁叠加成整棵树](https://img.arkblob.ccwu.cc/articles/deepseek-harness-design/chapters/01-everything-plugin/plugin-tree.jpg)

dsh 的底座是 Cordis，一个以“时空可组合性”为设计目标的插件框架（有配套论文）。五个核心概念：

- **插件即服务**：每个插件向共享上下文贡献一个服务，占据一个稳定的 `ctx.<key>`，比如 `ctx.tools`、`ctx.llm`、`ctx.sessions`。
- **上下文是容器**：插件之间通过 key 查找服务，而不是 import 具体实现——没有谁依赖谁，只有谁挂在哪。
- **依赖靠声明**：插件用 `inject` 声明所需服务，框架等它们就绪后再启动。加载顺序是依赖推导出来的，不是手写编排的。
- **类型化事件通信**：事件名通过类型声明合并注册，监听者类型安全。
- **注册是可逆副作用**：工具 schema、提示词片段、监听器都通过 `ctx.effect()` 安装，插件卸载或热重载时自动撤销，不留残骸。

运行中的 dsh 就是一棵插件树，由启动时按序叠加的层组合而成：**profile**（具名组装，如 `web`、`headless`、`sdk`）→ **bundle**（组合包，一组配置加挂载代码）→ **patch**（定位某个条目并整体替换，或插入新条目）。profile 自带的、用户自己的、命令行传入的 patch 依次叠加，任何一层都能改写下面的东西。

一条命令可以看穿全貌：`dsh --profile web --dump-config` 会打印出这台机器实际启动的整棵配置树——树上任何一个条目，都可以被你自己的 patch 换掉。**不存在需要打补丁的特权内核**：想扩展 dsh，不是去 fork 它，而是把自己的插件挂到它旁边。

## 能力 seam：换一个实现，改变整个产品

![图：黑板上画着 seam 三件套——服务定义、服务提供方、消费方三个圆圈，A鼠用箭头连接讲解](https://img.arkblob.ccwu.cc/articles/deepseek-harness-design/chapters/02-capability-seam/seam-triplet.jpg)

如果只能从 dsh 带走一个设计，我会选这个：**能力 seam（capability seam）**。

每项能力被拆成三件套一起设计：**Service Definition**（服务定义，接口与语义）、**Service Provider**（提供方，具体实现）、**Consumer**（消费方，通常是面向模型的工具）。文件系统、进程、终端、LLM、沙箱、审批，全部如此。

威力在于提供方可替换。举一个文档里的例子：文件系统访问和进程执行共享同一个“执行世界”——把 `ctx.fs` 的提供方从本地实现换成远程沙箱，Bash、PTY、LSP 这些消费方工具就整体搬进了沙箱，一行消费方代码都不用改。**换一个 provider，等于改变整个产品的形态。**

这种架构还带来一个反直觉的副产品：文档里的“能力图”是脚本从代码自动生成的——哪个包声明了服务、哪些包实现它、哪些包消费它，声明与调用点还能交叉校验。架构不再靠人肉维护的架构图讲故事，而是可以被工具持续验证的事实。

对照一下常见的做法：很多框架把工具实现直接焊死在核心里，想换执行环境只能 fork 或者加 if-else 分支。seam 的思路是把“能力的接口”当成一等公民先设计好，实现自然就可以插拔。

## 会话日志即唯一事实源

![图：A鼠指着黑板上一条仅追加的事件日志带，右侧从日志投射出消息历史的投影](https://img.arkblob.ccwu.cc/articles/deepseek-harness-design/chapters/03-session-log/log-projection.jpg)

第三块基石是会话数据的组织方式。dsh 的原则可以浓缩成一句话：**模型可见即已记录**。

会话是一条仅追加的 `SessionEvent` 日志。每次发给模型的请求，都必须能从这条日志重建——模型历史不是另存的数据，而是日志的投影（`deriveMessages()`）：从事件流回放出当时模型看到的世界。这带来了两个直接好处：

1. **可回放**。任何时刻打开旧会话，渲染的都是当年真实发生的事，包括审批决策、hook 调用、目标变更——它们全部落为持久事件，而不是散落在旁路日志里。
2. **可演进**。日志格式带版本化迁移链：vN 到 vN+1 单步迁移、排到发布链上、按格式指纹索引。老会话在新版本里照常打开，数据不会因为框架升级而作废。

事件本身分三个域，各有分工：**会话事件**（持久，追加进日志）、**agent 事件**（实时协调，如拦截请求、停止轮次）、**能力事件**（provider 层挂策略）。而且每个事件的分发模式是显式契约的一部分——`emit`（观察）、`waterfall`（带 `next()` 的环绕中间件，可短路）、`parallel`、`serial`、`bail`。想拦截还是想决策，从事件声明上一眼可见，不需要去读实现猜语义。

这套设计与 pi-durable 的 commit-before-show、Super-agent 的存算分离殊途同归：**把“发生过什么”做成唯一事实源，其余一切都是视图。**

## 这套设计意味着什么

![图：A鼠敲黑板，黑板上四个关键词——seam、事实源、事件契约、小核心](https://img.arkblob.ccwu.cc/articles/deepseek-harness-design/chapters/04-takeaways/takeaway-blackboard.jpg)

拉远了看，dsh 给 agent 框架设计留下了四个可迁移的思想：

- **能力 seam**：先设计“能力的接口”再设计实现。定义、提供方、消费方三件套齐全，能力才真正可插拔，执行环境的切换不再是 fork 级别的工程。
- **日志即事实源**：模型可见即已记录，历史是投影而非另存数据。上下文可重建、会话可回放、格式可迁移，这三件事都从这里自然长出来。
- **显式事件契约**：扩展点的语义（观察、包装、并行、短路）写在类型里，而不是藏在约定里。扩展行为因此可推理、可校验。
- **小核心加生态**：官方只维护最小核心，技能、MCP、浏览器、computer-use、团队协作全是生态插件，靠 plugin-market 分发。核心越小，演进越不被锁死。

局限同样清晰：它是单进程插件树（Cordis 同进程挂载），不是分布式方案；深度绑定 TypeScript 栈；开发者预览期破坏性变更是常态；个人 harness 产品形态与平台化嵌入场景并不完全重合。

所以更务实的问题不是“要不要用它替换什么”，而是：你的框架里，能力的接口是不是一等公民？发生过的事，是不是只有一份事实？扩展点的语义，是不是写在明面上？这三个问题答好了，无论用什么技术栈，都会得到一个更接近 dsh 的架构。
