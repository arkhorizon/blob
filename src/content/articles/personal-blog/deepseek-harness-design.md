今年 DeepSeek 开源了一个叫 Harness（简称 dsh）的 agent 框架，GitHub 上已经 27 万 star。它不是又一个套壳大模型 API 的项目，而是一个真的能用的产品：有 Web 界面、有桌面端、有命令行，聊天、跑工具、沙箱、审批、多人协作，全都齐了。

但功能多不是重点。真正值得看的是它的架构立场，一句话就能说完：**一切皆插件**。模型适配器是插件，工具注册表是插件，会话日志是插件，连 agent 主循环本身也是个插件。

这句话听着像口号，拆开看全是硬功夫。这篇文章就干一件事：把它的设计掰开揉碎，看看对任何想认真做 agent 框架的人有什么启发。

先打个预防针：dsh 还在开发者预览阶段，官方自己都说以后会有不兼容的改动。所以咱们聊的是设计，不是照着抄的代码。

## 一切皆插件：没有特权内核

![图：A鼠讲师站在黑板前讲解插件树，树根向上一层层的组合包与补丁叠加成整棵树](https://img.arkblob.ccwu.cc/articles/deepseek-harness-design/chapters/01-everything-plugin/plugin-tree.jpg)

dsh 的底座叫 Cordis，是 DeepSeek 自己写的插件框架，还配了一篇讲“时空可组合性”的论文。它的玩法不复杂，主要是这么几条规矩：

每个插件往外提供一个服务，占一个固定的位置，比如 `ctx.tools` 是工具注册表，`ctx.llm` 是模型层，`ctx.sessions` 是会话存储。插件之间想用别人的服务，按位置去找就行，谁也不用 import 谁。一个插件需要什么，自己声明清楚，框架会等这些东西就位了再启动它。工具描述、提示词片段、事件监听，凡是注册上去的东西都记着账，插件卸载的时候原样撤掉，不留下任何残余。

那么问题来了：这么多插件，是怎么拼成一整个产品的？答案是三层叠罗汉。最底下是 profile，相当于一份“菜单”，说明这次启动要用哪些组合包；中间是 bundle，组合包，打包好的一组功能和配置；最上面是 patch，补丁，看准树上的某个位置，整个换掉，或者塞个新的进去。启动的时候这三层按顺序叠上去，后叠的永远可以改写先叠的。

有个命令特别有意思：`dsh --profile web --dump-config`，它会把这台机器这次实际启动的整棵配置树打印出来。树上每一个节点，你都可以用自己的 patch 换掉。

这就是“没有特权内核”的意思：想改 dsh，不需要 fork 它、不需要给它打补丁，把自己的插件挂到它旁边就行。

## 能力 seam：换一个实现，改变整个产品

![图：黑板上画着 seam 三件套——服务定义、服务提供方、消费方三个圆圈，A鼠用箭头连接讲解](https://img.arkblob.ccwu.cc/articles/deepseek-harness-design/chapters/02-capability-seam/seam-triplet.jpg)

如果只能从 dsh 带走一样东西，我选 seam。

seam 是“接缝”的意思。dsh 把每一项能力都拆成三块来设计：先写一份服务定义，说清楚这项能力到底能干什么；然后是提供方，真正干活的实现；最后是消费方，用这个能力的工具。三块是一起设计的，边界切得干干净净。

光说概念太空，看两个真例子。

第一个是上网。dsh 给模型的上网工具就两个：`web_search` 和 `web_fetch`，这两个工具的参数格式永远不变，模型该怎么提交搜索词、怎么请求 URL，从头到尾一个样。但背后干活的实现是可以换的：搜索可以是 DeepSeek 自家的搜索服务，抓网页可以是普通的 HTTP 抓取器。哪天想换个搜索后端，改的只是提供方，模型毫无察觉——它看到的还是那两个工具，用法一模一样。

第二个更有意思，叫 Code Mode。开了这个模式之后，dsh 不再给模型一大堆工具的说明书，而是只给一个工具：`run_code`。模型想干什么，不再是一次次地调工具，而是写一小段程序，程序里爱调哪个能力就调哪个，跑完把结果拿回来。这里同样是一条 seam：契约是“执行一段模型写的程序，拿回它输出的内容”，提供方可以是一个 Worker 线程，也可以是一个独立进程，甚至将来是容器。执行后端换了，模型看到的还是那个 `run_code`，写的还是那种程序。

这两个例子背后是同一件事：**接口定死了，实现随便换**。很多框架做不到这一点，因为工具的实现和核心长在一起，想换个执行环境只能 fork 或者满地写 if-else。seam 的做法是先把“能力的接口”当成头等公民设计好，实现自然就能插拔。

这套设计还捎带一个好处：文档里的“能力图”是脚本从代码里自动生成的——哪个包声明了服务、哪些包实现它、哪些包在用它，一目了然，还能机器校验声明和调用对不对得上。架构图不再靠人肉维护，它是可以被验证的事实。

## 会话日志即唯一事实源

![图：A鼠指着黑板上一条仅追加的事件日志带，右侧从日志投射出消息历史的投影](https://img.arkblob.ccwu.cc/articles/deepseek-harness-design/chapters/03-session-log/log-projection.jpg)

dsh 处理会话数据的原则，一句话：**模型看得见的，一定记在日志里**。

整个会话是一条只增不改的事件日志。每回发给模型的请求，都必须能从这条日志原样重建出来——注意，模型“记得”的东西不是另存的一份历史，而是从日志里算出来的投影：拿着事件流倒放一遍，就能还原出模型当时看到的世界。

这样做好处很实际。第一，能回放：随时打开一个旧会话，看到的就是当时真实发生的事，中间哪次审批点了同意、哪个 hook 被触发了，全都记在日志里，不在别处。第二，能升级：日志格式带版本号，升级走一条链，v1 到 v2 一步迁移，老会话在新版本里照样打开，数据不会因为框架更新就废掉。

事件本身分三种：会话事件是持久化的，进日志；agent 事件是实时调度的，比如拦下某个请求、终止某一轮；能力事件挂在具体实现那一层。而且每种事件怎么分发是明说的，一共五种：有的是让大家看一眼就行，有的是监听器接力处理还能随时叫停，有的是并行跑，有的按顺序来，有的谁先有结论谁说了算。想观察还是想拍板，看事件声明就知道，不用去翻代码猜。

有意思的是，这套思路不是 dsh 独有的。pi 的 pi-durable 讲先落盘再显示，Super-agent 讲存算分离，说的其实是一件事：**把“发生过什么”做成唯一的事实，其余一切都是视图。**好的 agent 系统在这个问题上答案是趋同的。

## 这套设计意味着什么

![图：A鼠敲黑板，黑板上四个关键词——seam、事实源、事件契约、小核心](https://img.arkblob.ccwu.cc/articles/deepseek-harness-design/chapters/04-takeaways/takeaway-blackboard.jpg)

看完这三个设计，能带走的东西有四样。

能力接口要先于实现去设计。定义、提供方、消费方三块切干净，能力才真正可插拔，换执行环境才不用伤筋动骨。

日志要当事实源。模型看得见的都进日志，历史只是投影。做到这一点，会话能回放、上下文能重建、格式能升级，都是水到渠成的事。

扩展点的语义要写在明面上。一个扩展点到底是旁观的、能包装的、还是能一票否决的，从类型声明上看一眼就知道，不靠口头约定。

核心要小。dsh 官方自己只维护最小的核心，技能、浏览器、computer-use、多人协作，全是生态里的插件。核心越小，往前走的时候越不被自己绊住。

局限也得说清楚。它是单进程的插件树，不是分布式方案；深度绑定 TypeScript；预览期改动说变就变；而且它是给个人用的 harness 产品，跟平台化的嵌入场景并不完全是一回事。

所以更值得问的问题不是“要不要拿它替换什么”，而是三个自查：你的框架里，能力的接口是不是一等公民？发生过的事，是不是只有一份事实？扩展点的语义，是不是写在明面上？这三个问题想明白了，用什么技术栈，都能长出类似的架构。
